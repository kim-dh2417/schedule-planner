## 목적

이 문서는 일정관리 앱 MVP의 프론트 중심 아키텍처를 정리한다. 초기에는 화면 완성도와 상호작용 안정성을 우선하고, 이후 백엔드와 DB를 자연스럽게 연결하는 구조를 목표로 한다.

## 구조 원칙

- 프론트 우선 MVP로 시작한다.
- 데이터는 초기엔 로컬 상태 또는 mock 레이어로 관리한다.
- 화면 단위 컴포넌트와 도메인 상태를 분리한다.
- 나중에 API와 저장소를 교체해도 UI를 크게 바꾸지 않도록 한다.

## 제안 구조

- `src/App.jsx`: 전체 화면 조립
- `src/components/`: 공통 UI 컴포넌트
- `src/features/dashboard/`: 대시보드 전용 기능
- `src/features/schedules/`: 일정 데이터와 조작 로직
- `src/features/team/`: 팀 부하, 참여자, 상태 로직
- `src/data/mock/`: MVP 초기 더미 데이터
- `src/services/`: API 래퍼와 추후 교체 포인트

## 상태 흐름

1. 앱 시작 시 더미 데이터 또는 초기 API 응답을 로드한다.
2. 월간 캘린더와 Today Board를 같은 상태 소스로 렌더링한다.
3. Quick Draft에서 일정 초안을 만들면 로컬 상태를 즉시 갱신한다.
4. 일정 충돌이나 부하 경고는 계산된 상태로 화면에 반영한다.
5. 이후 API 도입 시 `services` 계층만 교체한다.

## 향후 백엔드 연계

- 일정 생성/수정/삭제는 API로 위임한다.
- 팀/참여자/집중블록은 서버 데이터로 관리한다.
- 요약 정보는 캐시 또는 집계 API로 분리한다.
- 인증/권한은 MVP 이후 별도 계층으로 도입한다.

## 배포 전제

- MVP 1차는 정적 프론트 빌드와 로컬 mock 데이터로도 동작해야 한다.
- 실제 서버는 추후 확장용이다.

## 리스크

- 초기부터 상태 구조가 복잡해지면 캘린더와 Today Board 동기화가 어려워질 수 있다.
- API와 로컬 mock의 데이터 모양이 달라지면 구현 비용이 커질 수 있다.

## 비고

- 이 문서는 기술 선택의 확정본이 아니라 초기 구조 초안이다.
- 서버 도입 시 추후 `아키텍처설계서_v2` 또는 별도 백엔드 설계서로 분리할 수 있다.
